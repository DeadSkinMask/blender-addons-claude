# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

Git repo `blender-addons-claude` (remote `origin` on GitHub, branch `master`): a folder of independent Blender 5.2 addon projects, one subfolder each. Built ZIPs are committed (the repo is for addons in general and the user installs from them); `test_log.txt` and screenshots are gitignored. Keep projects self-contained; don't share code between them. Code and comments in English, user-facing UI strings in Spanish (Sculpt Brush Shelf, Godot Level Bridge) — match the project you are in.

Blender 5.2.3 is installed at `/opt/blender-5.2.3-linux-x64/blender` (also `blender` on PATH). Target API is Blender 5.2 only; verify API names by running Blender (`blender -b --factory-startup --python-expr ...`), not from older docs.

## Sculpt Brush Shelf

Extension-format addon (`blender_manifest.toml`, no `bl_info`) that shows a user-defined short list of Sculpt Mode brushes in the 3D View sidebar (`N` → "Pinceles").

```bash
cd "Sculpt Brush Shelf"
./run_tests.sh /opt/blender-5.2.3-linux-x64/blender   # builds ZIP, runs headless tests, writes test_log.txt
./build_zip.sh                                         # only rebuild sculpt_brush_shelf-1.0.0.zip
```

- Tests are a single script (`sculpt_brush_shelf/tests/test_headless.py`) with named `check(...)` steps; there is no per-test selector — comment out entries in the list at the bottom to run a subset. It exits non-zero on any FAIL.
- `run_tests.sh` installs the ZIP as an extension into a temp `BLENDER_USER_CONFIG`/`BLENDER_USER_EXTENSIONS`, so the module under test is `bl_ext.user_default.sculpt_brush_shelf` and the user's real preferences are untouched. Always test the built ZIP, not the source folder.
- New files must be added to the `zip` command in `build_zip.sh` (it lists files explicitly). Bump the version in both `blender_manifest.toml` and `build_zip.sh`.
- Validate the manifest with `blender --command extension validate sculpt_brush_shelf`.
- Panel drawing, button highlight and preference persistence cannot be tested headless; the manual GUI checklist is in the project README.

Non-obvious API facts this addon depends on (verified on 5.2.3):
- Built-in brushes are assets; `bpy.data.brushes` is empty at startup. They are activated with `bpy.ops.brush.asset_activate(asset_library_type='ESSENTIALS', relative_asset_identifier='brushes/essentials_brushes-mesh_sculpt.blend/Brush/<Name>')`, which works in `--background` once in Sculpt Mode.
- Brush names are enumerated by `bpy.data.libraries.load(<DATAFILES>/assets/brushes/essentials_brushes-mesh_sculpt.blend, assets_only=True)`. Real names differ from the UI shorthand: `Inflate/Deflate`, `Pinch/Magnify`, `Flatten/Contrast`, `Crease Sharp`, `Draw Sharp`, `Relax Pinch`.
- Preferences cannot be written while registering, and no timers are used. Defaults are therefore applied lazily: `prefs.customized == False` means "use `DEFAULT_BRUSHES`"; any edit operator calls `materialize()` first to copy the defaults into the stored collection. Changing `DEFAULT_BRUSHES` only reaches users who have not customized the list.
- Dynamic enum items (`SCULPTSHELF_OT_add`) are kept in the module-level `_enum_items_ref` to avoid garbled strings.
- The native asset shelf cannot be filtered via public API, hence the custom panel.

`INSTRUCCIONES_ADDON_SCULPT_BRUSH_SHELF.md` is the original spec (written by GPT); its brush names and "tool region" panel placement were wrong, the implementation above supersedes it.

## Godot MultiMesh Scatter

Two files that form one pipeline and must stay in sync on the binary format. User-facing docs (setup, inspector properties, coordinate convention, troubleshooting) live in `README_Godot_MultiMesh_Scatter.md`; keep it updated when behavior changes.

- `godot_multimesh_scatter.py` (v1.1.0) — legacy addon (`bl_info`), installed by loading the single file via Preferences → Add-ons → Install from Disk. Sidebar tab "Godot". Exports a Geometry Nodes scatter host's instances as `scatter_transforms.bin` plus the source mesh as GLB, OBJ or both (`MESH_EXPORTERS` maps format → exporter).
- `GodotScatterBinaryLoader.gd` — `@tool` Godot 4 node (4.4+ for the Rebuild button) that builds a `MultiMeshInstance3D` from those two files, with an editor debug preview.

Contract shared by both: file starts with magic `GMMI0001`, then `uint32` instance count, then per instance 4 little-endian `float32` vec3 (basis columns x, y, z, then origin) already converted to Godot space (Blender `(x, y, z)` → Godot `(x, z, -y)`, via `C · M · C⁻¹` in `blender_to_godot_matrix`). Changing the format means editing the writer (`write_transforms`) and the loader together and bumping the magic. Mesh exporter axes (GLB `export_yup`, OBJ `up_axis='Y'`/`forward_axis='NEGATIVE_Z'`) must stay consistent with that same convention.

Gotchas: instance matrices come from `depsgraph.object_instances` and must be copied during iteration (items are only valid then). The mesh exporters change the selection, so `execute` restores the host as active afterwards. OBJ bakes the source object's transform into vertices, so the source mesh should have an identity transform. Export only works in Object Mode (operator `poll`). No automated tests exist for this project; it was used in practice before being formalized.

## Godot Level Bridge

Extension-format addon that exports a Blender level (one room per `.blend`) to a Godot 4.7 project as a manifest + GLBs; the Godot side is the `addons/level_bridge/` plugin inside the game repo `/home/luis/GIT/personal/Godot/elegia/` (its own git repo, with its own CLAUDE.md and tests). Docs in Spanish.

- `ANALISIS_Level_Bridge.md`: design and phases B0–B7. `FORMAT.md`: the manifest contract as implemented; change writer and reader together and update it. The joint order with the game phases is in `elegia/docs/plan_de_fases.md`.
- Current phase: **B0–B3 implemented** (addon 0.4.0; B3 = Geometry Nodes instances → MultiMesh, `instances.py`): scope, uids, validation, static GLB via staging copies, placeholders/markers/colliders/areas/paths. Module map: `scope.py` (what is exported + roles), `entities.py` (manifest entities, shapes, props, uids), `validate.py`, `static_export.py` (staging + glTF), `coords.py` (Blender→Godot), `godot_project.py` (layer names from project.godot), `export.py` (operators + orchestration), `ui.py`.

```bash
cd "Godot Level Bridge"
./run_tests.sh /opt/blender-5.2.3-linux-x64/blender   # builds ZIP, runs headless tests, writes test_log.txt
blender --command extension validate godot_level_bridge
/home/luis/GIT/personal/Godot/elegia/tests/run_all.sh  # Godot side
```

- Same test mechanics as Sculpt Brush Shelf (ZIP installed into a temp `BLENDER_USER_CONFIG`; module `bl_ext.user_default.godot_level_bridge`; `check(...)` list at the bottom of `tests/test_headless.py`). The test's second argument is a temp work dir where it fakes a Godot project.
- Fixtures shared with the game: `t_matches_godot_empty_fixture` and `t_sample_fixture_for_godot` compare Blender's output with `elegia/tests/fixtures/` (path via `GODOT_FIXTURES`). After changing the format run `UPDATE_FIXTURES=1 ./run_tests.sh …` to rewrite `fixtures/sample/` (manifest + GLB), then run the Godot tests. The sample level uses fixed uids so the output is deterministic.
- New files must be added to the `zip` command in `build_zip.sh`; bump the version there and in `blender_manifest.toml` (tagline max 64 chars).
- Upgrading on the user's machine: installing a new ZIP over the old one left the old code running (seen with 0.2.1→0.2.2 in the GUI; not reproducible headless with `package_install_files`). The documented procedure is Uninstall first, then install. When a fix "doesn't work" for the user, first check which version produced the output (e.g. the glTF scene name).
- Releasing a version: also copy the built ZIP to `/home/luis/GIT/personal/Godot/elegia/tools/blender/` (replacing the old one), since the user installs it from the game repo on another PC.
- Operators that `report({'ERROR'})` raise `RuntimeError` when called from Python; tests assert on that.
- The exporter must never modify the user's `.blend` data: static geometry goes through copies in a temporary scene (`static_export.py`), the original object is renamed only during the glTF export so the copy keeps its name (restored in `finally`), and the window scene is restored because the glTF exporter switches it. Only `gbridge.uid`/`uid_owner` are written. Files are written only when their content changes.
- Call `view_layer.update()` before reading `matrix_world` (validation does): transforms edited from Python are stale until then.
- `GLTFState.filename` in Godot has no extension (matters for the import extension's file filter).
- Geometry Nodes instances come in two kinds in `depsgraph.object_instances`: object instances (`inst.object.original` is the source) and geometry instances (`inst.object.original` is the host itself, `inst.object.data` is the instanced mesh). Copy `inst.object.data` during the iteration; `new_from_object(inst.object)` re-evaluates the host instead.
- Headless Godot uses a dummy renderer: `MultiMesh.get_instance_transform()` returns identity there, so tests check the `.gmmi` contents instead.

## RustRemesher

Quad remesher in two parts: `engine/` (Rust; only external crate is `rayon`) and later `addon/` (Python, Blender 5.2 extension) that calls it. Inspired by Quad Remesher's *bridge protocol* only (settings file, progress file, engine as a subprocess); the Quad Remesher binaries were not decompiled. The algorithm is a Rust port of SculptForge's "QRemesh 2" (github.com/islandmed/SculptForge, `src/core/QRemesh2*.cpp`, GPL-3.0) so the project is **GPL-3.0-or-later**: keep SPDX headers and credit it. No licensing, downloads or network anywhere. `FORMAT.md` is the addon↔engine contract (settings keys, progress file, binary mesh format with sections `COLR/MATL/SHRP/GUID`); change writer and reader together and bump the magic.

- Phases: 1 engine skeleton (**done**: CLI, settings, progress, binary+OBJ I/O, topology stats, cleaning) → 2 BVH + proxy surface (**done**: `bvh.rs`, `workmesh.rs` (triangulation, feature detection), `proxy.rs` (decimation + isotropic remeshing, parallel pre-decimation), `make_proxy` / `--proxy`; `run` still passes the mesh through) → 3 curvature + cross field (**done**: `complex.rs`, `solver.rs` (sparse matrix + aggregation multigrid + PCG, generic over real/complex, shared with the phase-4 map), `field.rs` (frames, curvature tensor, 4-RoSy field, matching + singularity index); `make_field` / `--field`) → 4 integer-grid map + extraction (**implemented, NOT yet committed**: `eliminator.rs`, `gridmap.rs`, `extract.rs`, `relax.rs`, `remesh.rs`; `run` now really remeshes, `--remesh <in> <out> [quads]`; see "Phase 4 status" below) → 4 integer-grid map + extraction → 5 hard edges/materials/vertex paint/symmetry/guides → 6 addon (path to the engine in preferences, curve guides) → 7 e2e tests, ZIP, docs.
- The exchange format is binary (not OBJ/FBX/glTF: OBJ keeps quads but is slow text and holds no attributes; glTF triangulates). Output mesh has new vertices/faces, no correspondence with the input.
- `cd RustRemesher/engine && cargo test` (unit + `tests/e2e.rs`, which runs the real binary); `./build.sh` builds `../dist/rustremesher` (Linux) and `../dist/rustremesher.exe` (cross-compiled with `cargo xwin`, static CRT, no VC++ redistributable); `./wine_smoke.sh` runs the exe under Wine.
- Wine 6.0.3 here lacks `bcryptprimitives.dll` (used by Rust std on Windows 10+), so `wine_smoke.sh` builds a test-only stand-in DLL (`tools/bcryptprimitives_shim`) next to a copy of the exe; never ship it. Use `wine64`, with `Z:` paths.
- Proxy facts: the proxy edge is `h0/3` (h0 = sqrt(area/target quads)), i.e. ~18 triangles per quad; hard edges = faces over 60° apart, chains shorter than 1.5·h0 dropped, user-marked ones (`SHRP`) always kept. `feature_info` must stay O(d log d): the O(d²) version took 66 s instead of 6 s on a 3M-triangle UV sphere (poles of valence 1500). Pre-decimation in 64 parallel blocks only kicks in when the source has > 8× the proxy triangles and > 300k. Dense input timing: 3M tris → 2000 quads 7 s, → 20000 quads 16 s (8 cores).
- Field facts: correctness is checked with Poincaré–Hopf, `Σ vertex_index == 4·Euler` (8 on a sphere, 0 on a torus), plus alignment with borders/hard edges/curvature. A sphere gets exactly the minimum 8 singularities and a torus 0. Everything sorted/blocked so results are identical for any thread count (tested 1 vs 4). Timing (8 cores): 2000 quads from a 3M-triangle sphere 5 s, 20000 quads 37 s.
- **Proxy quality bug found in phase 3** (invisible with icosphere tests): `collapse_ok` judged each triangle alone, so around the needle fans of a UV sphere's poles no collapse was allowed and those regions stayed undecimated (up to 70% thin triangles, 3.5× the triangles, field noise: 113 singularities). It now judges the worst triangle / longest edge of the whole neighbourhood and only refuses to make them worse. Use `rustremesher --proxy` (prints angles and regularity) and a UV-sphere source when touching `proxy.rs`; a few sub-20° triangles can remain on extreme poles (1000 segments: 0.06%).
- **Phase 4 status (stopped mid-way at the user's request; resume here).** Works: closed all-quad output for sphere (exactly 8 valence-3 poles, mean corner angle 4° off 90), torus (0 poles), cube/cylinder (hard edges and corners kept to 0.0005), blob, two separate pieces (split by connected components, quads ∝ area, min 24 each), open tube (0 poles, 0.0° error); 3M triangles → 20k quads in 16 s / <800 MB. Pieces that fail fall back to their source triangles (reported). A 36-run sweep (6 shapes × 30…20000 quads) had 0 failures/non-manifold/leftover triangles; tiny targets (30 quads) are poor. Phase 5 (engine side) is in, see below.
- **Phase 6 (addon, implemented).** `RustRemesher/addon/rustremesher/` is a Blender 5.2 extension (id `rustremesher`, version in `blender_manifest.toml` + `build_zip.sh`; UI/docs in Spanish). Modules: `exchange.py` (pure Python+numpy RRMI/RRMO writer/reader, mirrors `io_bin.rs`), `blender_io.py` (mesh → arrays with `foreach_get`, arrays → mesh with `foreach_set`; reads `obj.data`, never writes the source), `runner.py` (`find_engine`: prefs path → `bin/` in the addon → PATH; `EngineJob` runs `rustremesher -s settings.txt` in a temp dir and polls the progress file), `operators.py` (`rustremesher.remesh`: `invoke` = modal with a 0.3 s timer, Esc terminates the engine; `execute` = synchronous, used by tests and scripts; `start_job`/`finish_job` hold the logic), `guides.py` (curves in the `RR_Guides` collection → local-space polylines; Bezier sampled with `interpolate_bezier`), `props.py`, `prefs.py`, `ui.py`.
  - `cd RustRemesher/addon && ./run_tests.sh /opt/blender-5.2.3-linux-x64/blender` runs 15 headless checks against `../dist/rustremesher` (build the engine first; the ZIP is installed into a temp config like the other projects). `./run_gui_test.sh` is optional: it opens a real Blender window on `$DISPLAY` for a few seconds and drives the modal operator (progress, result, Esc via `xdotool`).
  - Operators that `report({'ERROR'})` raise `RuntimeError` from Python; tests assert on the Spanish messages. Source mesh with modifiers: off by default, `use_modifiers` reads `evaluated_get` through a temporary mesh. `UseIndexedNormals` is always sent as 0: split-normal edges are handled by sending Mark-Sharp edges as SHRP.
  - API facts verified on 5.2.3: `loop_total`/`loops.vertex_index`/`polygons.foreach_set` still work for building meshes; sharp edges are read with `edges.foreach_get('use_edge_sharp')` (the `sharp_edge` attribute does not exist until something is sharp); manifest `permissions.files` must be at most 64 characters.
- **Phase 5 (implemented; addon-side parts wait for phase 6).** `remesh.rs::relative_sizes` gives a relative size per proxy vertex from curvature (`CurvatureAdaptivness`, curvature measured at 2.5× the field's radius so the size does not change within a quad) and vertex-paint luminance (factor 3 each way), limited to 35% change per quad edge and smoothed; `size_base` normalises them to the wanted count; `proxy.field_size` makes the cross field turn with the size gradient (that creates singularity pairs at size extrema: a bumpy torus at adaptivness 100 gets ~18 pairs, at 50 ~7; blob stays clean). The proxy is rebuilt finer once when the smallest quads would get fewer than ~3 proxy edges. Materials: `WorkMesh` always carries groups when the input has MATL, `PieceResult.groups` takes the source group under each output face's centre, `remesh_mesh` writes MATL; `keep_groups` (UseMaterialIds) only decides whether group borders become loops. Guides are SOFT: `guide_segments` projects the curves on the surface and `FieldSettings.guide_angle/weight` pull the cross field to their tangent within `1 + 3·GuideStrength/100` quad edges (an exact on-curve loop is not possible: proxy feature edges come from source mesh edges, not from arbitrary segments; adding guide segments to `Features` does nothing). Symmetry (`symmetry.rs`): clip at the plane, remesh the positive half with target/2, `mirror_weld` (vertices within 0.05 quad edges of the plane are put on it and shared); guides are mirrored too; the result is ~5-7% under the count. `UseIndexedNormals` is the addon's job (mark split-normal edges as SHRP).
- **Phase 7 (real-world pass, implemented).** Real shapes exported from Blender (Suzanne, cone, beveled cylinder, subdivided Suzanne) exposed what the synthetic shapes hid: **low-poly input** (a few hundred triangles asked for thousands of quads) gave garbage (cone: 61 components, 735 flipped; Suzanne 835 poles at 5000). Fixes: (1) `subdiv.rs` — before the density loop `remesh_piece` splits every edge longer than 0.6 quad edges (red-green style, so needle triangles get fat), the new vertex on a smooth edge being the PN-triangle cubic midpoint from crease-aware corner normals (creases at ≥40°, open, or user-sharp edges stay straight), user sharp edges are split along; only coarse inputs are touched (the budget is 1.5M triangles). (2) `WorkMesh::from_mesh` triangulates convex n-gons with a star from an appended centre vertex (a 64-gon fan gave slivers); work-mesh vertex counts can therefore exceed the mesh's. (3) The size field is smoothed 64 rounds with amplitude 1.0 (was 16 / 1.2): the bevel cylinder went from 104 to 8 singularities. Remaining and expected: Suzanne's head keeps ~150-250 singularities at 5000 quads (its real creases are features; with AutoDetectHardEdges=0 and adaptivness 0: 57); `RR_TIMING=1` now also prints per-stage times of each piece (a noisy field made the head take 30 s). Cone at high counts: see "Known problem: cone" below.
  - `RustRemesher/release.sh [blender]` builds both binaries, runs cargo tests/clippy, the wine smoke test, the addon headless tests and `extension validate`, then packages `dist/release/`: addon ZIP without engine plus `-linux-x64` / `-windows-x64` ZIPs with the engine in `bin/` (manifest gets `platforms`), and installs the Linux one with no engine path set (`tests/test_bundled.py`). `runner.find_engine` restores the executable bit of `bin/rustremesher` (unzipping can drop it).
  - Real-shape sweep script idea: export primitives with `bpy.ops.wm.obj_export` in a Blender background run, then `--convert` + `-s settings.txt`; synthetic generators missed the low-poly failures completely.
- **Known problem: cone at high quad counts (documented to fix later, not fixed).**
  - *Reproduce:* in Blender `bpy.ops.mesh.primitive_cone_add(vertices=64)` (64 side triangles + one 64-gon cap, 65 vertices), export with `bpy.ops.wm.obj_export`, then `rustremesher --remesh cone.obj out.obj <quads>` (use `RR_TIMING=1` for stage times). Current engine (commit b074731), 8 cores:

    | quads | time | field singularities | flipped in map | poles | result |
    |---|---|---|---|---|---|
    | 200 | 0.2 s | 8 | 0 | 8 | clean |
    | 1000 | 1.6 s | 8 | ~60 | 12 | good |
    | 2000 | 7.9 s | 8 | 161 | 45 | closed, 1 component |
    | 3000 | 13 s | 8 | 238 | 78 | closed, 1 component |
    | 5000 | 21 s | 8 | 448 | 169 | closed, 1 component (an earlier build gave 2 components) |

  - *Facts measured:* the cross field is fine (always 8 singularities); the damage is in the integer map: flipped triangles grow with the count, and the extra poles (valence 3/5, in pairs) are scattered over the cone's side, none within 3 quad edges of the apex or of the base rim, so it is not a local apex or border defect like the hemisphere one. All three proxy densities fail the `poles <= 1.5·singularities + 4` test, so each run does the whole pipeline three times (each ~7 s at 5000: proxy 2.5 s, field 3 s, map 1.5–2.4 s) and keeps the best, which is why it is slow. The input first goes through `subdiv.rs` (128 triangles → thousands of well-shaped ones); before that fix the result was garbage, so the upsampling is not the culprit.
  - *Suspects, in order:* (1) the cone's side is developable with a 64-valent apex of large angle defect, and the 8 singularities sit around the apex and cap; the map's integer rounding then has to place many integer unknowns on a long thin region and 448 flips appear (compare the UV sphere, whose poles were fixed by the `collapse_ok` rewrite in phase 3: the same kind of trouble with a high-valence vertex, but there the proxy was the problem; here try dumping the proxy around the apex and checking triangle quality after `demote_soft_edges`). (2) The size field: at the default adaptivness 50 the curvature across the cone is strongly anisotropic, so sizes follow the circumferential curvature only; run with `CurvatureAdaptivness=0` to see if the flips drop (not yet tried on the cone). (3) The nearest-first integer rounding in `gridmap.rs` (frac 0.7 per round): try a smaller fraction or rounding by cone angle order. (4) The feature rim between the cap and the side (a 64-gon of hard edge, 3 pieces of feature chain?) pins integers: try `AutoDetectHardEdges=0`.
  - *How to investigate (what worked for the hemisphere):* dump the intermediate structure and plot it with matplotlib (it is installed) instead of theorising — e.g. write the lattice from `extract_lattice` and the per-corner `uv` of `GridMap`, mark the flipped triangles on the proxy, and see where they cluster; compare with `RR_TIMING` per attempt. The regression test to add when fixed: a 64-sided cone at 3000 quads, assert closed, one component, `poles <= 20`, no more than ~50 flipped.
- **Known problem: open surfaces at small counts (documented to fix later, not fixed).**
  - *What is left:* the jagged-rim bowl (my own test shape: a spherical cap with a noisy border, `bowl.obj` in the old scratchpad; recreate it as a hemisphere whose rim vertices are jittered ±30% of an edge) at a small target: 1000 quads → 15 poles for 6 field singularities, 114 boundary vertices, **184 flipped triangles in the map** (4000: 6 poles / 113 flipped; 12000: 5 / 49; 20000: 10 / 54). Clean-rim open surfaces (hemisphere, plate with a hole) are fine at every size tried, so the trouble is a noisy border at coarse resolution, not the open-surface machinery.
  - *Facts:* the extraction is not the culprit any more (the face tracing cap that caused 37 poles on the hemisphere is fixed and has a regression test); the poles come from the integer map (flipped triangles = rounding of integers along a border whose feature edges zig-zag at the proxy scale). The proxy keeps every border vertex of the source as a feature line, so a jittered rim gives feature segments whose direction changes faster than the quad size can follow.
  - *Suspects:* (1) smooth the border feature polyline at the quad scale before the proxy keeps it (a few Laplacian rounds along open-edge chains of the source, then project back as the projection step already does), so the lattice line can follow it; (2) in `gridmap.rs` the kind-2 (feature) integers are rounded together with the others by distance to the nearest integer — try rounding border integers first; (3) `demote_soft_edges` only judges sharp chains, never open borders: a short-wavelength zig-zag on a border could be demoted to a straight line like a soft crease.
  - *How to investigate:* same recipe as the hemisphere (dump the lattice, plot angle/height with matplotlib, mark flipped triangles on the proxy); regression test to add when fixed: hemisphere with a jittered rim at 1000 quads, `poles <= 10`, flipped `<= 30`.
- **Proxy density order (resolved).** `remesh_piece` now tries `DENSITIES = [3.0, 2.5, 3.2]` and accepts the first manifold result with `poles <= 1.5·singularities + 4`; otherwise it keeps the manifold result with the fewest poles. Measured: hemisphere 4000 quads went from 30 poles to the ideal 4. **Fixed (open surfaces with many poles at high counts)**: `extract_lattice`'s face tracing stopped any face at 64 vertices, so the "outside" face of an open surface with a longer border (a hemisphere's rim is ~250 nodes) came out in pieces that survived as odd faces with huge diagonals and dozens of extra poles. The lattice itself was perfect (checked by dumping it: only valence 3 on the border and at the 4 singularities, valence 4 elsewhere); the cap is now the number of half-edges. Hemisphere 12000: 37 → 4 poles. Regression test `open_surface_with_a_long_border_has_no_stray_faces` (hemisphere cut from a UV sphere; fails without the fix). Lesson: dump the intermediate structure and look at it (matplotlib is available) before theorizing; two earlier hypotheses (border `axis_of_edge`, pruning border seam leaves) were wrong. Status re-measured after phases 5-7 (the adaptive-size smoothing, upsampling and star n-gons changed these numbers): hemisphere 1000/4000/12000/20000 → 4/5/4/4 poles; a 120×120 plate with a square hole 1000…20000 → 0 poles; bowl 4000/12000/20000 → 6/5/10 poles for 8/8/10 field singularities. See "Known problem: open surfaces at small counts" below for what is left.
